Module 01: Core Architecture

The "Works on My Machine" Problem

Why traditional software deployment breaks across different operating systems and developer laptops.

❌ Without Docker

• Dev A is on Windows 11 with Node.js 20 installed.
• Dev B is on Ubuntu with Node.js 18.
• The production server runs Debian with Node.js 16.
• A package (like bcrypt) builds C++ binaries for Windows (.dll). When pushed to Linux, it crashes with invalid ELF header.
• Every new engineer spends 2 days setting up local databases, matching versions, and fixing path bugs.

✅ With Docker

• The application code, Node.js runtime, system libraries, and configs are packaged into a standardized Image.
• Dev A, Dev B, and the server all run the exact same Linux userland.
• Dependencies are compiled inside the Linux container, eliminating OS-specific binary errors.
• A new engineer runs one command: docker compose up, and the full stack is live in 60 seconds.

💡 The Core Truth: We don't ship our source code and pray the destination environment matches. We ship the entire working environment inside a sealed container.
Module 01: Core Architecture

Virtual Machines vs Containers

Why did the software industry move from heavy Hypervisors to lightweight Linux Containers?

Feature Virtual Machine (VMware / VirtualBox) Docker Container
Operating System Full Guest OS per VM (Ubuntu, Windows) Shares the Host OS Kernel
Isolation Layer Hypervisor (Type 1 or Type 2) Linux Namespaces & Control Groups (cgroups)
Resource Overhead Heavy: 10GB–40GB per VM, gigabytes of reserved RAM Lightweight: MegaBytes (10MB–200MB), shares host RAM dynamically
Boot Time Minutes (boots entire OS kernel and daemons) Milliseconds (just starts the isolated app process)
Density Can run ~5 to 10 VMs on a developer laptop Can run 50 to 100+ containers simultaneously
🧠 What is a Container under the hood? A container is NOT a mini-computer. It is simply a standard Linux process running on the host kernel, restricted by namespaces (isolates file system, network, process tree) and cgroups (restricts CPU and RAM usage).

Module 02: Application Baseline

Before Docker: Understanding `package.json`

How Docker reads your dependencies, scripts, and why `package*.json` is written with a wildcard.

backend/package.json 
{
  "name": "taskflow-backend",
  "scripts": {
    "start": "node src/server.js",
    "dev": "nodemon src/server.js"
  },
  "dependencies": {
    "express": "^4.18.2",
    "pg": "^8.11.3",
    "redis": "^4.6.10",
    "dotenv": "^16.3.1"
  },
  "devDependencies": {
    "nodemon": "^3.0.1"
  }
}

How Docker Uses Each Section

• `dependencies`: The libraries needed to run the API. When Docker executes RUN npm ci, it downloads and compiles these inside the Linux container.
• `scripts` ("start" & "dev"): Tells Docker what process to boot in CMD ["npm", "run", "dev"] or CMD ["node", "src/server.js"].
• `package-lock.json`: The frozen snapshot of exact SHA-512 hashes for every single sub-dependency.
⭐ Why write `COPY package*.json ./`?
The * is a wildcard. It copies package.json AND package-lock.json together without crashing if the lockfile hasn't been generated yet!

Why `npm ci` instead of `npm install` inside Docker?

npm install can update minor packages automatically and alter your lockfile. npm ci ("Clean Install") is read-only, strictly adheres to the lockfile, and is 2x faster because it bypasses dependency resolution. It guarantees 100% identical installs across all machines.

Module 02: Building Images

Anatomy of a Production Dockerfile

Every instruction explained line-by-line with caching optimization.

backend/Dockerfile 
# 1. Base runtime: pull official Linux image with Node 20 pre-installed
FROM node:20-alpine

# 2. Set the working directory inside the container (like cd /app)
WORKDIR /app

# 3. Copy package manifests FIRST (Cache Optimization!)
COPY package*.json ./

# 4. Install dependencies inside container during image build
RUN npm ci

# 5. Copy the application source code
COPY . .

# 6. Document which internal port the app binds to
EXPOSE 4000

# 7. Default command executed when container starts
CMD ["node", "src/server.js"]

❌ The Bad Way (Cache Busting)

WORKDIR /app
COPY . .
RUN npm install

What happens internally:
• Every time you change even a single comment or line in server.js, the hash of COPY . . changes.
• Docker sees that COPY . . changed, so it invalidates the cache for all subsequent steps.
• Docker is forced to re-run npm install from scratch on every single build.
• You wait 1–2 minutes every time you build.

✅ The Docker Way (Layer Cached)

WORKDIR /app
COPY package*.json ./  # Layer A
RUN npm ci             # Layer B
COPY . .               # Layer C

What happens internally:
• Editing server.js does NOT change package.json.
• Docker checks Layer A & B: CACHE HIT! It skips npm ci completely.
• Docker only executes Layer C (COPY . .), which copies files in 0.2 seconds.
• Your build is instant unless you actually add or remove a library.

Module 02: Building Images

The Essential .dockerignore File

Preventing heavy folders, host binaries, and secrets from polluting the build context.

What goes inside `.dockerignore`

.dockerignore 
node_modules
dist
build
.git
.env
*.log

What happens if you omit `.dockerignore`?

1. Massive Image Size: Docker will copy hundreds of megabytes of local node_modules into the build context, making builds painfully slow.

2. OS Incompatibility: Your Windows-compiled native C++ packages will overwrite the container's Linux modules, causing immediate crash.

3. Security Leak: Your private .env file (with database passwords and API keys) gets baked into the Docker image!

Rule of thumb: Always create a .dockerignore file in the same directory as your Dockerfile.

Module 04: Storage & Volumes

Volumes: Preventing Data Loss

Containers are ephemeral. If you delete a database container, where does your data go?

The Stateless Problem

When a container is deleted with docker rm, its thin writable layer is completely deleted.

If your PostgreSQL database saves records inside /var/lib/postgresql/data without a volume, all customer data is destroyed the moment you restart or update the container!

The Volume Solution

A Docker Volume is dedicated storage on the host machine filesystem that is mounted directly into the container directory.

Even if you destroy, update, or rebuild the container 1,000 times, the volume remains intact on your disk. The new container simply re-attaches to it!

🎯 Golden Rule: Applications (Node, Python, React) should be stateless (disposable). Databases (Postgres, MongoDB, Redis) must always use Volumes.
Module 04: Storage & Volumes

The 3 Types of Docker Mounts

Named Volumes, Bind Mounts, and Anonymous Volumes.

1. Named Volume

Managed completely by Docker.
Syntax: postgres_data:/var/lib/postgresql/data

Where is it stored locally?
• Linux: /var/lib/docker/volumes/
• Windows/Mac: Stored inside the WSL2 / Hyper-V virtual disk managed by Docker Desktop.

Best For: Production databases.

2. Bind Mount

Direct link to a specific folder on your laptop.
Syntax: ./backend:/app

Where is it stored locally?
Directly in your project folder on your Windows/Mac hard drive.

Best For: Development! Edit a file in VS Code → container updates instantly without rebuild.

3. Anonymous Volume

Volume without a host name.
Syntax: /app/node_modules

Why is this critical?
When you bind mount ./backend:/app, your host folder would wipe out the container's internal node_modules! Adding an anonymous volume tells Docker: "Keep container's node_modules isolated!"

🔍 Where is Named Volume Data Stored & How to View It?

Physical Location on Host Disk:
• Linux: /var/lib/docker/volumes/<vol_name>/_data
• Windows (Docker Desktop): Inside WSL2 virtual disk:
Paste in File Explorer address bar:
\\wsl$\docker-desktop-data\mnt\docker-desktop-disk\data\docker\volumes\

Docker Volume Management Commands:
• List all named volumes: docker volume ls
• Inspect exact host path: docker volume inspect 02-multi-container_postgres_data

Direct Command to View Postgres Database Files Live:
Terminal 
docker exec -it task_postgres ls -la /var/lib/postgresql/data

Flag breakdown: exec (execute command inside running container) • -it (interactive pseudo-terminal) • task_postgres (container name) • ls -la ... (lists all PostgreSQL table partitions, logs, and config files).

Module 05: Networking

Inter-Container Communication

Why does localhost fail between containers, and how does Docker's internal DNS solve it?

❌ Why localhost fails

Every container has its own private network stack and its own loopback address (127.0.0.1).

If your Express API container connects to DATABASE_URL="postgres://localhost:5432", it looks for Postgres inside itself and immediately crashes with ECONNREFUSED.

✅ Docker DNS & Service Names

Docker creates a custom virtual bridge network (e.g. app-network).

Docker has an automatic embedded DNS server. Containers can reach each other simply using the Service Name from Compose as the hostname!
DATABASE_URL="postgres://postgres:5432/taskflow"

Network Route:
Browser (localhost:80) ──▶ Nginx ──▶ api:4000 ──▶ postgres:5432 & redis:6379
Module 06: Engineering Workflow

Development Order: What to Write 1st, 2nd, 3rd?

The #1 confusion for new teams: "Do I write the Dockerfile first or docker-compose.yml first?"

1️⃣ STEP 1: Write `.dockerignore` (FIRST!)

Why first? Before you ever run a Docker command, you must protect your build context.
If you build before creating .dockerignore, Docker copies local node_modules, Windows .dll binaries, and secret .env files into your image.

2️⃣ STEP 2: Write `Dockerfile` (SECOND!)

Why second? A Dockerfile defines the blueprint for a single service (e.g. backend/Dockerfile).
You build and test your app as a standalone container first: docker build -t test-api ./backend. You ensure it boots cleanly.

3️⃣ STEP 3: Write `docker-compose.yml` (THIRD!)

Why third? You cannot compose what does not exist yet!
Now that your custom app has a Dockerfile, Compose references it with build: ./backend and wires it to databases (postgres:16), caches (redis:7), and networks.

4️⃣ STEP 4: Configure `.env` & Run (FOURTH!)

Why fourth? Externalize all passwords and secrets out of the compose file.
Create .env.example for Git, fill in real values in .env, and execute: docker compose up --build!

🎯 The Golden Rule: Dockerfile is 2nd, YAML is 3rd! Dockerfile builds the individual building block; Docker Compose glues all blocks together into a neighborhood.
Module 06: Multi-Container Orchestration

Orchestrating with docker-compose.yml

Instead of typing 5 massive `docker run` commands with 30 flags, define the entire stack in one file.

docker-compose.yml 
version: '3.8'

networks:
  app-network:
    driver: bridge

volumes:
  postgres_data:
  redis_data:

services:
  # 1. Database Service
  postgres:
    image: postgres:16-alpine
    container_name: task_postgres
    environment:
      POSTGRES_USER: taskuser
      POSTGRES_PASSWORD: taskpass123
      POSTGRES_DB: taskflow
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./scripts/init.sql:/docker-entrypoint-initdb.d/init.sql
    networks:
      - app-network

  # 2. Node.js Backend API
  api:
    build:
      context: ./backend
      target: development
    container_name: task_api
    environment:
      PORT: 4000
      DATABASE_URL: postgresql://taskuser:taskpass123@postgres:5432/taskflow
      REDIS_URL: redis://redis:6379
    ports:
      - "4000:4000"
    volumes:
      - ./backend:/app
      - /app/node_modules
    depends_on:
      - postgres
    networks:
      - app-network

Every Key in docker-compose.yml Explained Line-by-Line

Key What It Does Internally Why We Write It
networks: app-network Creates a virtual bridge network with an internal DNS resolver Allows containers to communicate using service names (e.g. postgres:5432) instead of dynamic IPs
volumes: postgres_data Registers a persistent directory on the host machine filesystem Ensures database rows survive even if the container is stopped or rebuilt
build: context + target Tells Docker which directory to build and which multi-stage stage to compile Runs target: development locally, and target: production on servers
ports: "4000:4000" Creates an iptables forwarding rule: HostPort:ContainerPort Lets your browser on localhost:4000 send traffic into the container's private port
volumes: ./backend:/app Sets up a Bind Mount between host folder and container folder Enables instant Hot Reload—code edits on your laptop reflect live inside container
volumes: /app/node_modules Creates an Anonymous Volume Prevents your host's Windows node_modules from wiping out container's Linux modules
depends_on: postgres Controls container startup sequence Ensures the database is booting before the API process attempts to connect

Module 09: Production Automation

CI/CD Pipeline with Docker & GitHub Actions

How modern teams push to Git, build Docker images in CI, and deploy to servers with zero downtime.

The 4-Step Automated Pipeline

1. Code Push: Developer runs git push origin main.
2. CI Runner Build & Test: GitHub Actions spins up an isolated Ubuntu runner and builds the Docker image: docker build -t myusername/api:latest .
3. Push to Registry: The runner signs into Docker Hub / AWS ECR using encrypted repository secrets and pushes the verified image.
4. Automated Server Deploy: An SSH hook triggers the production server: docker compose pull && docker compose up -d.

Why Docker Revolutionized CI/CD

• Zero Environment Drift: You don't install Node, Python, or Postgres versions on the CI runner VM. The container already has everything.

• Fast Rollbacks: If a deployment has a critical bug, rolling back doesn't require recompiling code. You simply run: docker run myusername/api:v1.0.4 (the previous image tag), and you are rolled back in 2 seconds.

• Immutable Artifacts: The exact same image tested in CI is what runs on production servers.

.github/workflows/deploy.yml 
name: Build and Deploy to Production

on:
  push:
    branches: [ main ]

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Strict CI Dependency Install & Test
        run: |
          cd backend
          npm ci
          npm test

      - name: Log in to Docker Hub
        uses: docker/login-action@v2
        with:
          username: ${{ secrets.DOCKER_USERNAME }}
          password: ${{ secrets.DOCKER_TOKEN }}

      - name: Build and Push Docker Image
        uses: docker/build-push-action@v4
        with:
          context: ./backend
          push: true
          tags: myusername/taskflow-api:latest

      - name: Deploy on Remote Server via SSH
        uses: appleboy/ssh-action@master
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SERVER_SSH_KEY }}
          script: |
            cd /home/ubuntu/app
            docker compose pull
            docker compose up -d --remove-orphans
Module 09: Production CI/CD

npm install vs npm ci in CI/CD & Docker

Why automated pipelines mandate npm ci, and why missing lockfiles cause the dreaded EUSAGE crash.

Comparing the Two Commands

Behavior npm install npm ci (Clean Install)
Primary Target Local Dev & Bootstrapping CI/CD Pipelines & Production
Requires Lockfile? No (creates one if missing) Strictly Mandatory (fails if missing)
node_modules Overwrites / adds diff Deletes & reinstalls clean
Version Drift Can drift on caret ^1.2.0 100% frozen bit-for-bit match
Speed in CI Resolves tree (~20-40s) 2x-3x faster (skips resolution)

The Real-World CI/CD Scenario

• The Trap: If your Dockerfile has RUN npm ci, but you never generated a package-lock.json on your host laptop, Docker halts the build with:
npm error The `npm ci` command can only install with an existing package-lock.json • Why we use npm install for local bootstrap: It works cleanly without requiring a pre-existing host lockfile.
• How to promote to strict CI/CD: Generate lockfile on host:
npm install --package-lock-only Commit package-lock.json to Git, then switch Dockerfile to RUN npm ci!

🎯 Core Takeaway: "Use npm install during initial scaffolding. Use npm ci inside automated CI/CD runners to enforce 100% deterministic, bit-for-bit identical builds."
Module 10: Technical Deep-Dive

"If Git exists, why do we need Docker?"

Understanding the technical boundary between source version control and OS runtime isolation.

What Git DOES and DOES NOT do

✔ Tracks text code changes and commit history.
❌ DOES NOT track the operating system kernel.
❌ DOES NOT install PostgreSQL, Redis, or Nginx.
❌ DOES NOT lock system-level C-libraries (glibc/OpenSSL).
❌ DOES NOT prevent Windows vs Linux compile bugs.

What Docker delivers

✔ Bundles the exact Linux OS userland.
✔ Bundles the exact runtime version (Node 20.10, Python 3.11).
✔ Spins up databases and caches with zero local setup.
✔ Compiles dependencies inside the target Linux environment.
✔ Delivers a 100% reproducible execution boundary.

🏗️ The Paper Blueprint vs Pre-Fabricated Room Analogy

Git is the paper blueprint. If you hand someone a blueprint, they still have to buy the bricks, hire the plumbers, and hope the local water pressure matches.
Docker is the pre-fabricated room. The walls, wiring, plumbing, and appliances are already hooked up and tested inside a shipping container. You just drop it on the ground and plug in power.

Module 11: Enterprise Security

Docker Security & Non-Root Execution

Eliminating the #1 container vulnerability: why default root access enables kernel breakout.

❌ The Default Root Trap (UID 0)

• In standard base images (node:20-alpine, python:3.11), container processes run as root (UID 0) by default.

• The Breach Path: If an attacker discovers a Remote Code Execution (RCE) vulnerability in your Express/FastAPI app or a 3rd-party dependency, they immediately execute shell commands as root inside the container.

• Kernel Escape Risk: From root inside a container, breaking out to the host Linux kernel (via mounted Docker sockets, system capabilities, or kernel CVEs) is vastly easier.

• Audit Failure: SOC 2, ISO 27001, and CIS Docker Benchmark Rule 4.1 strictly flag root-level containers as critical audit findings.

✅ Hardened Non-Root Implementation

Create a dedicated system user and switch to it before launching the process:

Dockerfile (Production Stage) 
# 1. Create unprivileged group & user
RUN addgroup -g 1001 -S nodejs && \
    adduser -S -u 1001 -G nodejs nodejs

# 2. Assign files to the unprivileged user
COPY --chown=nodejs:nodejs . .

# 3. Drop root privileges completely
USER nodejs

EXPOSE 4000
CMD ["node", "src/server.js"]
🛡️ Verification Command: Run docker exec -it task_api id. A secure container outputs uid=1001(nodejs) gid=1001(nodejs) instead of uid=0(root).
Module 11: Enterprise Tooling

Multi-Architecture Builds (docker buildx)

Bridging the Apple Silicon (ARM64) vs Cloud Server (AMD64 / x86_64) hardware gap.

The Hardware Mismatch Problem

• Developers write and build code on Apple Silicon MacBooks (ARM64 / aarch64 architecture).

• Cloud servers (AWS EC2, GCP Compute, DigitalOcean) typically run on AMD64 (x86_64) architecture.

• The Crash: If an image is built on ARM64 and pushed directly to an AMD64 production server, the container crashes instantly on startup with:
exec /usr/local/bin/node: exec format error • The Reason: CPU machine instructions compiled for ARM cannot execute on Intel/AMD x86 processors without cross-compilation.

The OCI Multi-Platform Solution

docker buildx bundles BuildKit with QEMU CPU emulation to generate a single image tag containing binary manifests for both CPU architectures:

Terminal (Cross-Compile & Push) 
# 1. Initialize multi-platform builder instance
docker buildx create --name enterprise-builder --use

# 2. Build for both architectures & push multi-arch manifest
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t mycompany/taskflow-api:v1.0.0 \
  --push ./backend

✔ Cloud registries (Docker Hub / AWS ECR) automatically serve the exact matching architecture layer when pulled by an M-series Mac or an AMD64 server.

🌐 Universal Compatibility: One image tag (mycompany/api:v1.0.0) works flawlessly across Developer Laptops (ARM64), CI/CD Runners, and Cloud Kubernetes clusters (AMD64).
Module 11: Production Reliability

Resource Governance & Graceful Shutdowns

Preventing host RAM exhaustion (OOM Killer Exit 137) and dropped in-flight HTTP requests.

1. Memory Ceilings & The OOM Killer (Exit 137)

• By default, a Docker container can consume 100% of host RAM and CPU.

• If a runaway analytical query or memory leak occurs, the host kernel triggers the Linux OOM (Out-Of-Memory) Killer.

• The OOM Killer instantly kills the container with Exit Code 137 (128 + 9 SIGKILL) without logging an error in your app.

• The Fix in Compose: Throttle hard limits to protect host neighbors: 

deploy:
  resources:
    limits:
      cpus: '0.50'       # Cap at 50% single CPU core
      memory: 512M       # Hard memory ceiling
    reservations:
      memory: 256M       # Guaranteed baseline

2. SIGTERM Handling & Zero-Downtime Draining

• When rolling deployments or docker stop execute, Docker sends SIGTERM, waits stop_grace_period (default 10s), then forcibly issues SIGKILL.

• Without Handling: In-flight user requests are terminated mid-stream, dropping checkout transactions and corrupting state.

• With Handling: Node/FastAPI drains active requests, closes database pools, and exits cleanly: 

// Node.js / Express Graceful Draining
process.on('SIGTERM', () => {
  server.close(async () => {
    await db.end();      // Close PostgreSQL pool
    await cache.quit();  // Disconnect Redis
    process.exit(0);     // Clean exit code 0
  });
});
🎯 Zero-Downtime Guarantee: Combining stop_grace_period: 15s in Docker Compose with application SIGTERM connection draining ensures 100% of in-flight user requests finish before the old container retires.
