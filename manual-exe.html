STEP 3
Write Backend Multi-Stage Dockerfile
backend/Dockerfile

Create backend/Dockerfile with layer caching & dev/prod targets:

backend/Dockerfile 
# 1. Base & Dependency Layer
FROM node:20-alpine AS base
WORKDIR /app
COPY package*.json ./
RUN npm install

# 2. Development Stage (Live coding via bind mounts)
FROM base AS development
ENV NODE_ENV=development
COPY . .
EXPOSE 4000
CMD ["npm", "run", "dev"]

# 3. Production Stage (Hardened non-root runner)
FROM node:20-alpine AS production
WORKDIR /app
ENV NODE_ENV=production

# Security: Dedicated system user & group (SOC 2 / CIS Benchmark)
RUN addgroup -g 1001 -S nodejs && adduser -S -u 1001 -G nodejs nodejs

COPY package*.json ./
RUN npm install --omit=dev

COPY --chown=nodejs:nodejs . .

# Drop privileges from root (UID 0) to nodejs (UID 1001)
USER nodejs

EXPOSE 4000
CMD ["node", "src/server.js"]
📐 Layer Caching Strategy: Independent Dependency Invalidation COPY package*.json ./ and RUN npm install precede application source code. Docker caches this dependency layer. Subsequent application source code edits never invalidate the dependency cache or trigger package re-installation.
🛡️ Security Benchmark: Non-Root Execution (SOC 2 & CIS Compliance)

Why Root is Dangerous: Default base images run processes as root (UID 0). If an attacker exploits an application vulnerability (e.g. Remote Code Execution), they inherit root privileges inside the container, drastically simplifying host kernel privilege escalation.

Hardening: Creating nodejs (UID 1001) and declaring USER nodejs ensures the runtime process operates with the least privilege required, passing enterprise compliance audits.

🔒 CI/CD Determinism Specification: npm ci vs npm install Policy

Architecture Decision: "In automated production CI/CD pipelines, npm ci is mandated for bit-for-bit reproducible builds. npm ci strictly requires an existing, committed package-lock.json (failing with EUSAGE if missing). For zero-friction repository onboarding without pre-existing host lockfiles, npm install is utilized for local bootstrapping. Prior to production release tagging, lockfiles are generated and frozen via RUN npm ci."

▶ CI/CD Lockfile Generation & Strict Enforcement Procedure
1. Generate host lockfile without downloading host node_modules:
cd backend; npm install --package-lock-only; cd ..

2. Update Dockerfile to strict CI mode:
- RUN npm install
+ RUN npm ci (and RUN npm ci --omit=dev for production)
STEP 4
Write Frontend Multi-Stage Dockerfile
frontend/Dockerfile

Create frontend/Dockerfile (Vite dev server + Nginx production server):

frontend/Dockerfile 
# 1. Base & Dependencies
FROM node:20-alpine AS base
WORKDIR /app
COPY package*.json ./
RUN npm install

# 2. Development Stage (Vite Dev Server)
FROM base AS development
COPY . .
EXPOSE 3000
CMD ["npx", "vite", "--host", "0.0.0.0", "--port", "3000"]

# 3. Production Stage (Build React & serve with Nginx)
FROM base AS build
COPY . .
RUN npm run build

FROM nginx:alpine AS production
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
📐 Multi-Stage Optimization: Static Nginx Production Footprint Node.js runtime is strictly discarded for client-side assets in production. The build stage compiles JSX/TSX into minified static bundles, which are copied into an ultra-lean (25MB) Alpine Nginx server.
🔒 Frontend Deterministic Build Policy

Policy Specification: "Identical determinism rule: npm ci requires an existing, committed package-lock.json. In automated production CI/CD pipelines, commit frontend/package-lock.json and switch line 395 to RUN npm ci to prevent unexpected React or Vite minor version bumps from introducing runtime regressions."

STEP 5
Write Root docker-compose.yml
docker-compose.yml

In the multi-container track (02-multi-container/), create docker-compose.yml:

docker-compose.yml 
networks:
  app-network:
    driver: bridge

volumes:
  postgres_data:
  redis_data:

services:
  # 1. Database (PostgreSQL 16)
  postgres:
    image: postgres:16-alpine
    container_name: task_postgres
    environment:
      POSTGRES_USER: taskuser
      POSTGRES_PASSWORD: taskpass123
      POSTGRES_DB: taskflow
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./scripts/init.sql:/docker-entrypoint-initdb.d/init.sql
    networks:
      - app-network

  # 2. Cache (Redis 7)
  redis:
    image: redis:7-alpine
    container_name: task_redis
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    networks:
      - app-network

  # 3. Express Backend API
  api:
    build:
      context: ./backend
      target: development
    container_name: task_api
    stop_grace_period: 15s
    deploy:
      resources:
        limits:
          cpus: '0.50'
          memory: 512M
        reservations:
          cpus: '0.25'
          memory: 256M
    environment:
      PORT: 4000
      DATABASE_URL: postgresql://taskuser:taskpass123@postgres:5432/taskflow
      REDIS_URL: redis://redis:6379
    ports:
      - "4000:4000"
    volumes:
      - ./backend:/app
      - /app/node_modules
    depends_on:
      - postgres
      - redis
    networks:
      - app-network

  # 4. React Frontend
  frontend:
    build:
      context: ./frontend
      target: development
    container_name: task_frontend
    ports:
      - "3000:3000"
    volumes:
      - ./frontend:/app
      - /app/node_modules
    depends_on:
      - api
    networks:
      - app-network
📐 Service Discovery & Virtual Bridge Network Routing DATABASE_URL routes to @postgres:5432 rather than localhost. Inside Docker's isolated user-defined bridge network, services communicate by service name via Docker's embedded DNS server.
⚡ Resource Governance & Graceful Termination (OOM 137 & SIGTERM)

OOM Killer Protection: Without memory limits, runaway queries or memory leaks consume 100% of host RAM until the Linux kernel terminates the container with Exit Code 137 (128 + 9 SIGKILL). Enforcing memory: 512M isolates resource impact.

Zero-Downtime Draining: When rolling updates or docker stop run, Docker sends SIGTERM. Setting stop_grace_period: 15s grants Node/Express 15 seconds to drain active client requests, finish database writes, and close pools before Docker forcefully issues SIGKILL.

STEP 8
Multi-Architecture Cross-Compilation (docker buildx)
Terminal

Compile production images targeting both Apple Silicon (ARM64) and Cloud Servers (AMD64 / x86_64) simultaneously to prevent exec format error:

Terminal (PowerShell) 
# 1. Initialize and switch to a multi-platform Buildx builder instance
docker buildx create --name enterprise-builder --use

# 2. Build multi-arch OCI image manifest for AMD64 & ARM64
docker buildx build --platform linux/amd64,linux/arm64 -t myusername/taskflow-api:latest ./backend
🌐 Cross-Compilation Architecture Rationale Modern software teams develop on ARM64 (M-Series MacBooks) while production environments deploy on AMD64 (AWS EC2 / GCP). docker buildx leverages QEMU emulation and OCI Multi-Platform Manifests so one single tag runs natively on every hardware architecture without binary mismatch crashes.
