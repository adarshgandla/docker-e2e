3 Words — That's All

Before we type anything,
know just 3 words.

📄

Dockerfile

Your recipe. Plain text file. You write it once. It tells Docker exactly how to build your app's box.

📦

Image

The sealed box. Built from the Dockerfile. Read-only. You can share it. You can run it anywhere.

🏃

The box, open and running. Like pressing Play on an Image. One image → run 10 identical containers.

🍪 The cookie cutter is your Image. The cookie it produces is your Container. One cutter — unlimited identical cookies. (Same Containers always)
Step 1 — The Recipe

📄 Writing the Dockerfile
Telling Docker how to build your box

# What base do we start from?
FROM node:20-alpine

# Where inside the box do we work?
WORKDIR /app

# Copy the shopping list (package.json) first
COPY package*.json ./

# Buy everything on the shopping list
RUN npm install

# Now pack everything else into the box
COPY . .

# Which door does the box open on?
EXPOSE 4000

# When someone opens the box, what starts?
CMD ["node", "src/server.js"]
Step 2 — Pack the Box

📦 Building the Image
docker build = sealing the box

Docker reads your Dockerfile top to bottom and creates a sealed, portable image. Each instruction adds a layer — like packing one item at a time.

🧱Layer 1Base OS — node:20-alpine (the foundation)
🧱Layer 2Working directory set inside the box
🧱Layer 3npm install — all packages installed
🧱Layer 4Your source code — packed inside
📦Final Image — sealed, ready, portable
⚡ Layers are cached. If your code changes, only the last layer rebuilds. The rest reuse the cache. Builds are fast.

Step 4 — Unpack It

🎁 Running a Container
docker run = opening the box

When someone runs the image, Docker creates a container — the image comes alive. Isolated. Fast. Disposable.

docker run -d -p 8080:80 nginx
-d Run in background (detached — no logs flooding your terminal)
-p 8080:80 Map YOUR port 8080 → container's port 80 (so your browser can reach it)
nginx Which image to run (pulls from Docker Hub if not local)
Then open http://localhost:8080 — Nginx web server, running inside a box, reachable in your browser. Took 5 seconds.
Terminal Now docker run -d -p 8080:80 --name demo-nginx nginx → open localhost:8080

How They Talk

Port Mapping &
Container Communication

Two rules. Know these and networking in Docker makes complete sense.

RULE 1 — HOST → CONTAINER
Port Mapping

Your browser can't go inside Docker. So you open a door — map a host port to a container port.

🧑 Browser localhost:3000 → container:3000
🧑 Browser localhost:4000 → container:4000
🔧 DBeaver localhost:5432 → postgres:5432
Format: "HOST:CONTAINER" in docker-compose.yml
RULE 2 — CONTAINER → CONTAINER
Service Names as Hostnames

Inside Docker's network, containers find each other using the service name — not localhost.

api → connects to → postgres:5432 ✅
api → connects to → localhost:5432 ❌
frontend → connects to → api:4000 ✅
localhost inside a container = that container itself, not another container
🧑 Browser :80 ──▶ nginx ──▶ api:4000 ──▶ postgres:5432 & redis:6379 Each arrow uses the service name — Docker resolves it automatically inside the network

1. If Git exists, why do we need Docker?

When a colleague asks: "Why can't we just push and pull code with Git?"

WHAT GIT DOES

✔ Tracks text code files (.js, .py, .html)
✔ Tracks commit history & branches
❌ DOES NOT track the operating system
❌ DOES NOT install PostgreSQL, Redis, or Nginx
❌ DOES NOT manage Node/Python runtime versions
❌ DOES NOT prevent Windows vs Linux compile errors

WHAT DOCKER PACKS

✔ The exact OS (e.g. Alpine Linux)
✔ The exact runtime (e.g. Node 20.10.0, Python 3.11)
✔ The exact database binaries (Postgres 16, Redis 7)
✔ All system libraries (OpenSSL, glibc)
✔ Your code bundled and tested inside it

💥 The Real-World Failure Scenario with Git alone

You write code on Windows 11 with Node 20. A package uses a native C++ module (e.g., bcrypt or sharp). When you run npm install, your Windows compiler creates a .dll / Windows binary. Your colleague is on Ubuntu or macOS. They run git pull. Git pulls the code, but the app crashes because Windows binaries don't run on Linux, their Node is Node 18, and PostgreSQL isn't installed. They spend 3 hours setting up what Docker solves in 60 seconds.

🏗️ The Analogy: Git is the architect's blueprint on paper. Handing someone the blueprint means they still have to find bricks, hire plumbers, and hope water pressure matches. Docker is the pre-fabricated shipping container room with plumbing and electricity pre-installed.

2. Architectural Choice: Option A vs Option B

How to answer: "Should we host it on one server or install on every computer?"

Model Where Docker Runs What Team Needs Best Used For
Option A
Central Server / Office Box		 On ONE machine (e.g. your PC or office server) Just a Web Browser Demoing, Staging, QA, Clients.
Colleagues open http://IP:80. They don't install Docker or touch code.
Option B
Cross-Dev on every laptop		 On EACH developer's computer Git + Docker Desktop Active Development.
Developers edit files locally; bind mount reflects changes instantly.
🎯 The Practical Verdict:
• Use Option B for developers who write code and need their own isolated testing sandbox.
• Use Option A when presenting or giving colleagues a live demo without setup overhead.

3. The 2015-Style Manual Execution Plan

Senior systems engineer checklist — zero magic, verified end-to-end:

Step 1 — Verify Local Ports: Before running, confirm no local software (local Postgres, IIS, Apache) is hogging ports 80, 3000, 4000, or 5432.
Step 2 — The 4 Core Files:
  ① backend/Dockerfile — multi-stage (base, dev, prod).
  ② frontend/Dockerfile — Vite dev / Nginx prod.
  ③ scripts/init.sql — auto-seeds database on first launch.
  ④ Root docker-compose.yml — links all 4 services together on app-network.
Step 3 — Start the Stack: docker compose up --build.
Step 4 — Validate Every Link in the Chain:
  • Database link: Look for ✅ PostgreSQL connected & ✅ Redis connected in API logs.
  • Backend Direct: Visit http://localhost:4000/api/tasks (returns live DB JSON).
  • Reverse Proxy / UI: Visit http://localhost:3000 or http://localhost:80 (React UI fetches from API).
Step 5 — Sharing with a Colleague: Colleague runs git clone, copies .env.example to .env, and runs docker compose up --build. Exactly 60 seconds later, everything runs identically on their machine.
